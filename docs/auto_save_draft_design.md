# 日记(Entry)自动保存草稿与回收站功能技术规范书

## 1. 功能概述与目标

本规范书旨在定义日记系统自动保存草稿与回收站功能的技术实现标准。核心目标是构建一套高可靠的内容保护机制，消除用户因意外（如网络中断、浏览器崩溃、误操作）导致的数据丢失风险，并提供完善的“软删除”与恢复机制。

**特别说明**：本方案基于复用现有数据库结构的原则，不涉及任何数据库模式（Schema）变更或数据迁移操作。

## 2. 核心术语与数据模型

### 2.1 术语定义

- **日记条目 (Entry)**：用户编写的具体日记内容单元，对应数据库中的实体记录。
- **草稿 (Draft)**：用户正在编辑但尚未正式发布的日记条目。此类内容仅作者可见，不参与公共聚合或展示。
- **回收站 (Recycle Bin)**：存放用户执行“删除”操作后的日记条目。处于此状态的条目在保留期内可被恢复，过期后将被系统自动清除。
- **静默保存 (Silent Save)**：在后台异步执行的保存操作，不阻断用户界面交互，不显示模态对话框，仅提供轻量级的视觉反馈。
- **已发布 (Active)**：处于正常可见状态的日记条目。

### 2.2 数据模型映射 (复用现有 br_entry 表)

利用 `br_entry` 表现有的字段来实现状态管理和时间记录，无需新增字段。

| 逻辑属性         | 对应 DB 字段      | 类型      | 描述                                             |
| :--------------- | :---------------- | :-------- | :----------------------------------------------- |
| **状态**         | `status`          | `TINYINT` | 状态标识：`0`-回收站, `1`-已发布(正常), `2`-草稿 |
| **最后保存时间** | `update_utc_time` | `BIGINT`  | 草稿的自动保存时间、已发布日记的最后修改时间     |
| **删除时间**     | `update_utc_time` | `BIGINT`  | 当 `status=0` 时，此字段记录进入回收站的时间     |
| **创建时间**     | `add_utc_time`    | `BIGINT`  | 草稿首次创建的时间                               |

### 2.4 配置项 (`.env.local`)

```bash
# 自动保存策略
IDIARY_AUTO_SAVE_ENABLED=true         # 全局开关，默认开启
IDIARY_AUTO_SAVE_INTERVAL=60000       # 自动保存触发间隔（毫秒），默认 60s

# 回收站策略
IDIARY_RECYCLE_BIN_ENABLED=true       # 回收站功能开关
IDIARY_RECYCLE_BIN_RETENTION_DAYS=30  # 回收站保留天数，超过自动清理
```

## 3. 后端架构与逻辑设计

### 3.1 自动保存逻辑流程

后端需提供专门的接口处理自动保存请求。该接口的处理逻辑如下：

1.  **请求接收**：接收包含日记ID（可选）、日记本ID、标题、内容、状态以及客户端时间戳的请求。
2.  **新建草稿判断**：
    - 若请求中未包含日记ID，视为新建草稿请求。
    - 创建一条新记录，强制将其状态设置为“草稿状态”，并记录当前时间。
3.  **更新现有草稿**：
    - 若请求包含日记ID，查询数据库获取对应记录。
    - **状态保护检查**：检查该记录当前的状态。若记录处于“正常状态”（已发布），则**禁止**通过自动保存接口进行覆盖更新，以防止未完成的草稿意外覆盖已发布的正式内容。此时应返回错误，指示前端转为本地缓存策略。
    - 若记录处于“草稿状态”，则正常更新其标题、内容及更新时间。
4.  **响应返回**：返回保存后的日记ID、服务端保存时间及版本信息。前端在接收到新创建的 `diary_id` 后，应立即更新当前编辑上下文，后续请求均携带此 ID。

### 3.2 列表查询增强逻辑

日记列表查询功能需进行扩展，支持根据状态参数过滤结果：

- **默认模式**：仅返回状态为“正常状态”的日记。
- **草稿箱模式**：仅返回状态为“草稿状态”的日记，按更新时间倒序排列。
- **回收站模式**：仅返回状态为“回收站状态”的日记，按删除时间（即更新时间）倒序排列。

### 3.3 回收站管理逻辑

- **软删除（移入回收站）**：
  - 接收删除请求。
  - 将目标日记的状态更新为“回收站状态”。
  - 将更新时间刷新为当前时间（作为删除时间戳）。
- **恢复（从回收站还原）**：
  - 接收恢复请求。
  - 将目标日记的状态更新为“正常状态”。
  - 可选：保留原删除时间或刷新为当前时间。
- **彻底删除**：
  - 接收彻底删除请求。
  - 物理删除该日记记录。
  - 级联物理删除与该日记关联的所有评论、点赞等附属数据。
- **自动清理任务**：
  - 系统需运行定时任务（如每日一次）。
  - 扫描所有状态为“回收站状态”且更新时间早于保留期限（如 30 天前）的记录。
  - 对这些过期记录执行物理删除操作。

## 4. 前端架构与交互设计

### 4.1 编辑器状态机与保存策略

前端编辑器需维护一个内部状态机，管理从输入到保存的完整生命周期，并简化状态流转：

- **状态流转**：
  - **空闲 (Idle)**：初始状态或保存完成后的状态。
  - **保存中 (Saving)**：定时器触发自动保存，正在发起网络请求或写入本地缓存。
  - **保存失败 (Error)**：保存操作遭遇错误。

- **差异化保存策略**：
  1.  **新建日记场景**：
      - 初始无 `diary_id`。
      - 第一次自动保存成功后，后端返回生成的 `diary_id`。
      - 前端更新当前编辑上下文，后续所有自动保存请求均携带此 `diary_id`，作为对现有草稿的更新。
  2.  **编辑已发布日记场景**：
      - 仅在服务端保存失败（如网络中断）时，降级为**本地保存**（LocalStorage），以防止数据丢失。
      - 若服务端保存成功，则**不**写入本地缓存，保持本地环境整洁。
  3.  **发布与保存互斥**：
      - 当用户点击“发布”按钮时，系统应立即**暂停或取消**正在进行的自动保存定时器。
      - 使用当前编辑器中的最新内容提交发布请求，成功后更新页面状态，避免自动保存请求在发布后异步到达导致时序混乱。

### 4.2 核心交互设计

- **定时触发机制**：
  - 不再监听键盘输入事件。
  - 使用 `setInterval` 根据配置的 `IDIARY_AUTO_SAVE_INTERVAL` 周期性触发保存检查。
- **内容变化检测**：
  - 定时器触发时，对比当前编辑器内容与上一次成功保存的内容。
  - **仅当内容发生变化时**，才执行实际的保存操作（网络请求或本地写入）。若内容无变化，则跳过本次保存。
- **网络容灾**：
  - 当云端自动保存因网络问题失败时，自动降级为本地保存。
  - UI 应明确提示网络异常及数据已本地暂存的状态。
  - 网络恢复后，尝试自动同步或提示用户手动同步。
- **状态反馈**：
  - 编辑器需提供显式的状态指示器（如状态栏文字或图标）。
  - 明确展示“保存中”、“已保存（含时间）”、“保存失败”等状态。

### 4.3 界面模块设计

- **草稿箱页面**：
  - 展示所有草稿状态的日记列表。
  - 列表项包含标题、摘要及最后保存时间。
  - 提供“编辑”和“删除”操作入口。
- **回收站页面**：
  - 展示所有回收站状态的日记列表。
  - 列表项包含标题、删除时间及剩余保留天数（根据保留期动态计算）。
  - 提供“恢复”和“彻底删除”操作入口。

## 5. 异常处理与边界情况

- **网络中断与恢复**：当自动保存因网络原因失败时，前端应将当前内容写入本地缓存（LocalStorage）作为兜底。一旦检测到网络恢复，或用户重新打开页面，应检查本地缓存并提示用户是否恢复未保存的内容。
- **本地缓存恢复**：当用户打开编辑器时，若检测到存在对应的本地缓存且时间晚于服务端数据，应主动提示用户“发现未保存的本地副本”，并提供加载副本的选项。

## 6. 性能优化要点

- **增量检查**：前端必须严格执行脏检查，杜绝无意义的重复提交。
- **请求频率控制**：后端应对自动保存接口实施速率限制（Rate Limiting），防止恶意刷接口或前端逻辑错误导致的流量风暴。
- **索引优化**：确保数据库中状态字段和更新时间字段建有合适的索引，以保障草稿箱和回收站列表查询的高效性，特别是针对回收站自动清理任务的范围查询。

## 7. 实施步骤

1.  **后端逻辑实现**：在服务层实现自动保存、软删除、恢复、彻底删除及自动清理的核心逻辑，并确保不影响现有业务流程。
2.  **API 接口开发**：暴露并测试相关 HTTP 接口，确保权限验证和参数校验完备。
3.  **前端核心封装**：开发自动保存管理器模块，封装防抖、脏检查、状态机及本地存储逻辑。
4.  **UI 界面开发**：完成草稿箱、回收站列表页及编辑器状态栏的开发与对接。
5.  **集成测试与验证**：重点验证新建日记云端同步、已发布日记本地兜底、断网容灾及回收站自动清理等关键场景。
