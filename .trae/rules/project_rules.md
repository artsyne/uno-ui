## 代码质量要求
### 重构要求
**核心重构原则：业务逻辑和外部接口契约不变性**

请严格遵守以下规则对提供的 Go 语言代码进行重构。任何违反这些规则的修改都将被视为无效或不符合要求：

1.  **业务逻辑（Behavioral Logic）必须保持完全一致：**
    * **禁止** 修改任何函数或方法的内部核心逻辑，包括但不限于：
        * 算法、计算公式、数据转换规则。
        * 条件判断（`if/else`, `switch`）、循环（`for`）、流程控制。
        * 对数据状态的读写操作（例如，数据库操作、缓存操作、文件 I/O）。
        * 验证规则、业务决策点。
        * 任何会改变最终输出结果或产生副作用的行为。
    * **错误处理逻辑：**
        * **禁止** 改变现有错误返回的条件、类型、顺序和内容（特别是 `github.com/biuren/hebe/internal/core/error` 包定义的 `*errors.AppError` 类型及其 `Code` 和 `Key`）。
        * **禁止** 增加或删除现有公共 API 的错误返回路径。
    * **总之，在相同输入条件下，重构后的代码必须产生与原代码完全相同的输出和副作用。**

2.  **外部接口（External API）契约必须保持完全不变：**
    * **所有导出的接口（`interface`）**：其中定义的所有方法的 **签名（方法名称、参数列表的类型、顺序、数量，以及返回值列表的类型、顺序、数量）必须保持不变**。
    * **所有外部可访问的公共函数和方法（即被其他包调用的 `func` 和方法）**：它们的 **签名（函数/方法名称、参数列表的类型、顺序、数量，以及返回值列表的类型、顺序、数量）必须保持不变**。
    * **禁止** 对任何这些公共签名进行任何形式的修改，例如增加/删除参数、改变参数类型、改变返回值类型、改变方法/函数名称。

3.  **允许的重构类型（在不违反上述原则的前提下）：**
    * **依赖关系调整：** 引入、修改或优化组件之间的依赖注入（DI）关系。
    * **包（`package`）的重命名或新增：** 允许对包进行逻辑上的拆分、合并或重命名，以提高模块化和内聚性。
    * **文件（`file`）的重命名与组织：** 允许调整文件和目录结构，以提高代码的可读性和维护性。
    * **内部名称修改：** 允许修改 **包内部、未导出（小写开头）的方法、函数、结构体和变量的名称**，以优化命名清晰度。
    * **代码移动：** 允许将相关代码从一个文件或函数移动到另一个更合适的上下文，只要不改变其外部可见行为。
    * **类型定义内部字段名称（如果外部不直接访问）**：允许修改结构体内部字段的名称，前提是这些字段不通过公共方法暴露或不直接被外部包通过字段名访问。

**重构目标：**
在严格遵守上述不变性原则的前提下，通过以下方式优化代码：
* 解决现有代码中已识别的循环依赖问题。
* 提高模块的内聚性、降低模块间耦合度。
* 提升代码的可测试性。
* 改善代码结构和可读性。

**请在您的重构方案中，清晰地列出并说明您进行了哪些符合上述规则的修改，以及这些修改如何帮助实现重构目标。**
